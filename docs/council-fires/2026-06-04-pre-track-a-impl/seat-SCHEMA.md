# SCHEMA seat — Pre-Track-A implementation review (2026-06-04)

## Q1 — Repository pattern shape
- **Disposition**: MAJOR
- **Claim**: One module per table under `src/skill_harness/storage/repositories/` (10 evidence + 5 runtime), **functional** `insert_<table>(conn, ...) -> <Row>` API, no class wrappers. Evidence repos export ONLY `insert_*` + `get_*` + `select_*`; no `update_*` / `delete_*` exists at the module surface. Defense-in-depth: (a) mypy `__all__` excludes mutating verbs, (b) at the module top, `from typing import Final` plus a runtime `_FORBIDDEN: Final[frozenset[str]] = frozenset({"update","delete","mutate"})` asserted by a `tests/test_repository_surface.py` AST-walker that fails CI if any `repositories/evidence/*.py` defines a function whose name starts with `update_`/`delete_`. SQL strings live per-repo (~10 INSERTs each, not enough to justify a query builder; a builder hides the literal SQL that A1 triggers RAISE against, hurting reviewability). Pydantic `strict=True` at the *write boundary* (inside `insert_*` it constructs the Row model first, then binds). Read paths return `Row` dataclasses, not Pydantic — read is hotter and the schema is the validator (CHECK constraints).
- **Evidence**: `PLAN.md:107-111` exit criteria; `migrations/evidence/0001_initial.sql:111-138` (oracle_verdicts multi-line CHECK = ten constraints repos must respect); `COUNCIL_FINDINGS.md` A1 trigger names map 1:1 to module names.
- **Recommendation**: Track A subagent specs a `repositories/evidence/__init__.py` that re-exports only `insert_*`/`get_*`/`select_*` and the AST-walker test. Functional shape; defer class wrappers to a v0.2 refactor IF a real reason emerges.
- **What-would-change-it**: If TEST-ARCH demonstrates that the Hypothesis strategy needs stateful `Connection` carrying (RuleBasedStateMachine), a class shape becomes weakly justifiable.
- **Cross-seat**: TEST-ARCH owns the AST-walker test spec.

## Q2 — Dual-DB transaction primitive
- **Disposition**: BLOCKER
- **Claim**: **Load-bearing rule: evidence is the source of truth; runtime gaps are reconcilable from evidence.** Sequence is fixed: write evidence FIRST (with `synchronous=FULL`, A22), then write runtime. A crash between the two leaves an audit row with no cost-ledger entry — recoverable by a reconciler that scans `evidence.oracle_verdicts` for verdicts lacking a paired `runtime.cost_ledger` row and back-fills with `reconciled=1`. The inverse order (runtime first) would let the cost ledger claim spend for an evidence row that never persisted — a "we charged for nothing" silent loss. `ATTACH DATABASE` is **forbidden** for production code paths: it would let `synchronous=NORMAL` on the attached side downgrade durability semantics for the primary, and SQLite's atomic-commit-across-attached-DBs requires a single journal mode neither DB is configured for. ATTACH may be used READ-ONLY in `skill audit` (D7).
- **Evidence**: A22 (`COUNCIL_FINDINGS.md` Appendix B); SQLite ATTACH+WAL interaction (https://www.sqlite.org/wal.html §"WAL does not work over a network filesystem" + ATTACH journal-mode coupling); A3 admissibility snapshot semantics (verdict carries everything needed to recover).
- **Recommendation**: Track A subagent specs `storage/dual_write.py` with `write_verdict_with_cost(evidence_conn, runtime_conn, verdict_row, cost_row)`. Inside: BEGIN IMMEDIATE on evidence → INSERT verdict → COMMIT evidence → BEGIN on runtime → INSERT cost_ledger → COMMIT runtime. If runtime COMMIT fails, log `crash_window_open` and emit reconciler-eligible record. Phase 1.5a-style smoke test: kill the process between commits and verify the reconciler restores invariants.
- **What-would-change-it**: If RELIABILITY produces a concrete crash-injection test showing the gap window is bounded and recovery is automatic, severity drops to MAJOR.
- **Cross-seat**: RELIABILITY owns the reconciler implementation; SECURITY confirms the gap window doesn't widen an attack surface.

## Q3 — Single-writer queue
- **Disposition**: MAJOR
- **Claim**: "Single writer per DB" comes from APPLICATION discipline, NOT from OS lock and NOT from SQLite WAL writer-exclusion (those are correctness floors, not the source). Implementation: in-process `threading.Lock` wrapping every repo's `insert_*` call, one Lock instance per DB attached to the Connection (not module-global; supports the test pattern of multiple isolated DBs). v0.1 assumes single-process. Multi-process is out of scope (CLAUDE.md "Repo status"). Track D's parallel sample-generation: subject API calls happen concurrently (no Lock), but their `insert_samples` + `insert_oracle_verdicts` writes serialize through the evidence Lock. If verdicts produce faster than the writer drains (unlikely: API latency >> SQLite COMMIT latency at synchronous=FULL ≈ 5-50ms), backpressure is signaled via a `queue.Queue` with `maxsize=64` and `put(timeout=30)` raising `WriterBackpressureError` (new typed exception).
- **Evidence**: `src/skill_harness/storage/migrations.py:208` `isolation_level=None` autocommit (no implicit writer queue); A22 synchronous=FULL fsync per COMMIT (~10ms on SSD).
- **Recommendation**: Track A subagent specs `storage/single_writer.py` exposing `WriterQueue(conn)` context manager. Repos use `with writer_queue(evidence_conn): conn.execute(...)`.
- **What-would-change-it**: If RELIABILITY argues that `multiprocessing.Lock` is needed for v0.1 because the CLI dispatches subprocess workers, severity rises to BLOCKER. Pre-respond: PLAN §"TRACK D" + claude-api skill imply in-process async, not subprocess.
- **Cross-seat**: RELIABILITY co-owns this — backpressure policy is theirs.

## Q4 — Property-based test design
- **Disposition**: MAJOR
- **Claim**: `@composite` strategies parameterized per-table, FK-aware via stateful generation: a top-level `evidence_state_machine` (Hypothesis `RuleBasedStateMachine`) draws `insert_skills` → then can draw `insert_clauses(skill_id=draws_from_existing_skills)` etc. The append-only property is asserted as an `@invariant`: after every successful INSERT, attempt `UPDATE` and `DELETE` on the same row and assert `sqlite3.IntegrityError` with the table-specific message. CHECK constraints (`comparator IN (...)`, `oracle_tier IN (1,2,3)`, the 10-line oracle_verdicts XOR check) are encoded as Hypothesis `st.sampled_from` — DO NOT let Hypothesis generate arbitrary strings for these or 99% of draws fail. UNIQUE constraints (`skills.skill_id` PK, `clauses.UNIQUE(skill_id, clause_index)`) handled by tracking generated tuples in the state machine and using `assume(not_yet_generated)`. **The trap**: `runs.completed_at` is the one *legitimate* UPDATE on an evidence table — the invariant must EXEMPT `runs` UPDATEs OF `completed_at` from NULL OLD value. A naive invariant test would flag the set-once UPDATE as a property violation. Use a `@rule` for `complete_run` separately from `@invariant` for "no UPDATE succeeds."
- **Evidence**: `migrations/evidence/0001_initial.sql:38-41` clause CHECKs; `0001_initial.sql:121,127-138` verdict CHECKs; `0002_runs_trigger_split.sql:20-25` set-once semantics.
- **Recommendation**: Track A subagent specs `tests/test_evidence_append_only_property.py::EvidenceAppendOnlyMachine` with the rule/invariant split described.
- **What-would-change-it**: If TEST-ARCH counters that stateful machines over-constrain falsification, fallback is `@given(insert_payload=valid_insert_strategy(table=st.sampled_from(EVIDENCE_TABLES)))` with FK satisfied by pre-seeding a fixture skill.
- **Cross-seat**: TEST-ARCH owns the strategy *design*; SCHEMA owns the constraints they must honor (this output).

## Q5 — Connection lifecycle
- **Disposition**: MINOR
- **Claim**: Long-lived connection per process per DB, owned by an application-level `StorageContext` dataclass (`evidence_conn`, `runtime_conn`, both opened at CLI entry, closed in `finally`). Repos do NOT own connections (would force every repo call to revalidate PRAGMAs). The `contextlib.contextmanager` "writer transaction" wrapper from Q3 is layered on top. WAL requires the writer to keep its connection open for readers to see passive-checkpoint progress (https://www.sqlite.org/wal.html §"Avoiding Excessively Large WAL Files") — long-lived connection satisfies this naturally. `synchronous=FULL` cost (fsync per COMMIT) is amortized by batching INSERTs inside a single `BEGIN IMMEDIATE`/`COMMIT` where multiple writes are causally one event (e.g., a `run` insert + its first `samples` insert).
- **Evidence**: `migrations.py:208-213` (PRAGMAs set on open; per-call open would re-pay PRAGMA cost).
- **Recommendation**: Track A subagent adds `storage/context.py::StorageContext` (dataclass + `open()` + `close()` + `__enter__`/`__exit__`).
- **What-would-change-it**: If RELIABILITY shows the WAL checkpoint pressure becomes pathological at scale, per-batch checkpoint pragmas become needed (deferred).
- **Cross-seat**: RELIABILITY owns the checkpoint cadence.

## Q6 — Admissibility filter on read
- **Disposition**: BLOCKER
- **Claim**: **Default-on filtered.** The repo surface exposes `select_verdicts_for_aggregation(conn, clause_id) -> list[Row]` which hard-codes `WHERE admissibility_state = 'admissible' AND verdict_id NOT IN (SELECT verdict_id FROM confound_events WHERE delta_kind='confound_flagged')`. An audit-only `select_verdicts_for_audit(conn, ...)` returns everything, including inadmissible + confounded, with no SQL filter. The names are load-bearing: `_for_aggregation` vs `_for_audit` makes the wrong-call obvious at call site (Track E grep-able). CLAUDE.md "Aggregation rules" is unambiguous — silent inclusion of inadmissible evidence is the highest-confidence-erosion bug in the system; an explicit-opt-in API can be missed once in Track E and corrupt every claim. The dual-API widening is a feature, not a cost: it forces audit callers to *say* they are auditing.
- **Evidence**: CLAUDE.md "Aggregation rules" verbatim ("Only verdicts that are both admissible AND non-confounded enter aggregation"); A3 (`COUNCIL_FINDINGS.md`) write-time snapshot makes the SQL filter cheap (no joins); A11 confound semantics require the second filter clause.
- **Recommendation**: Track A subagent specs exactly two read functions on `oracle_verdicts` repo; aggregation-mode is default. Add `tests/test_admissibility_default_filter.py` that inserts 2 admissible + 1 inadmissible + 1 confounded and asserts `_for_aggregation` returns the 2; `_for_audit` returns 4.
- **What-would-change-it**: If TEST-ARCH demonstrates that the default-on filter creates a vacuity hazard ("0 results returned looks identical whether there's no data or all inadmissible"), add a `count_inadmissible_for_clause()` companion.
- **Cross-seat**: TEST-ARCH owns the vacuity-vs-inadmissible distinction (A17); this Q is its storage-side manifestation.

## Q7 — Migration sequencing across worktrees
- **Disposition**: MAJOR
- **Claim**: Reserve number ranges per track in `PLAN.md` BEFORE Phase 2 dispatch. Specifically: Track A may reserve `0003-0009` on both `migrations/evidence/` and `migrations/runtime/`; Track C reserves `0010-0019`; Track D reserves `0020-0029`; Track E reserves `0030-0039`. Why ranges not timestamps: the SHA-256 ledger (A4) is order-sensitive — `apply_pending` discovers in sorted-string order, and two migrations with the same numeric prefix from different worktrees would collide deterministically AND the SHA mismatch would manifest as `MigrationTamperedError` on the second-merged worktree's first open. Timestamps don't help because they don't enforce mutual exclusion. Reserved ranges + a PR-time check (`migrations/evidence/` lint that fails CI if two PRs claim the same number) catches the collision pre-merge.
- **Evidence**: `migrations.py:69-88` `discover()` uses `sorted(directory.glob("*.sql"))` — string sort; `COUNCIL_FINDINGS.md` A4 SHA-256 ledger; PLAN.md §"Phase 2" worktree dispatch.
- **Recommendation**: Track A subagent updates `PLAN.md` Phase 2 section with the range table BEFORE writing any new migration. Add `scripts/check_migration_ranges.py` invoked by the (future) CI Stop hook.
- **What-would-change-it**: If the team adopts a "main-merge-serializes-migrations" rule via PR labels, ranges become optional convention rather than load-bearing.
- **Cross-seat**: RELIABILITY co-owns the merge-conflict recovery path; SECURITY confirms that range gaps don't trip the ledger's `_split_statements` invariant.
