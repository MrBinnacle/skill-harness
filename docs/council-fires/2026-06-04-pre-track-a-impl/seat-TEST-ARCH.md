## Q1 — Repository pattern shape
- **Disposition**: MAJOR
- **Claim**: "Repo enforces append-only at the API surface" is a vacuity-prone spec unless made syntactically testable. The trigger layer (A1) already enforces the invariant at SQL — the repo-surface guarantee is a DEFENSE-IN-DEPTH overlay, not a primary contract. Falsifying-case template: `import inspect; for repo in evidence_repos: assert not any(re.match(r'^(update|delete|set|patch|modify|remove)_', n) for n in dir(repo))`. mypy `Final`/protocol-based enforcement is weaker — a developer who adds `update_skill()` will type-check fine because Python's open-class shape doesn't carry "thou shalt not add methods" through mypy. Adopt: per-table module under `src/skill_harness/storage/evidence/repositories/{table}.py`; module-level functions only (no class needed; classes invite subclass-override escape hatches); Pydantic `model_config = ConfigDict(strict=True, extra='forbid')` at write boundary so unknown kwargs fail loud.
- **Evidence**: `migrations/evidence/0001_initial.sql:183-200` (triggers handle SQL-layer); PLAN §TRACK A "Repository module per table"; PRD §17 "deterministic Python layer owns... storage"; CLAUDE.md "any code that writes to an evidence table must use the repository APIs from Track A, never direct SQL."
- **Recommendation**: Track A adds `tests/test_evidence_repo_surface.py` with two falsifying-case tests: (1) name-regex AST scan over every module in `storage/evidence/repositories/` rejecting `update_*|delete_*|set_*|patch_*|remove_*` prefixes; (2) for each public function, Pydantic-validated dataclass input with `extra='forbid'`.
- **What-would-change-it**: If repos return SQLAlchemy/ORM session objects rather than executing writes themselves, the surface-scan becomes pointless because mutation moves to caller. Functional-only writes keep the scan honest.
- **Cross-seat**: SCHEMA co-owns the trigger-vs-API layering question. SECURITY co-owns "what if someone bypasses the repo via raw `sqlite3.connect`" — A23/PRAGMA-scope is the answer.

## Q2 — Dual-DB transaction primitive
- **Disposition**: MAJOR
- **Claim**: Two SQLite connections, no 2PC, evidence-FIRST ordering is the correct asymmetry: a verdict in `evidence.db` with no matching `runtime.cost_ledger` row is recoverable (cost re-derived from ledger of API metadata in evidence side or written off); a `runtime.cost_ledger` charge with no verdict is silently-lost evidence. Falsifying-case template: `def test_partial_dual_write_leaves_evidence_only(monkeypatch): monkeypatch.setattr(runtime_repo, 'insert_cost_row', lambda *a: raise IOError); write_verdict(...); assert verdict in evidence; assert no row in runtime.cost_ledger; assert reconciler queue flagged the orphan`. This is a HAND-ROLLED fault-injection test, NOT Hypothesis — the failure mode is binary (write-succeeds-or-not) and exhausts in O(n_call_sites).
- **Evidence**: `migrations.py:208` `isolation_level=None` (autocommit per-statement); A3 admissibility snapshot at write time means evidence rows are self-contained; CLAUDE.md "Aggregation rules: only admissible+non-confounded enter aggregation" — runtime never enters aggregation.
- **Recommendation**: Track A implements `dual_write(evidence_op, runtime_op)` helper that executes evidence-first, catches runtime exception, logs structured `dual_write_partial` event, returns sentinel. Add `tests/test_dual_write_partial.py` with `unittest.mock.patch` fault injection on each of the 3 known dual-write call sites (verdict+cost, run-start+budget, calibration_event+current_calibration pointer).
- **What-would-change-it**: If runtime writes become part of admissibility (e.g., cost-exhausted runs flagged `inadmissible_budget`), runtime becomes load-bearing and ordering must flip or a reconciler becomes mandatory.
- **Cross-seat**: RELIABILITY owns crash-safety. SECURITY owns "what if attacker can pause one of the two writes" — same answer.

## Q3 — Single-writer queue
- **Disposition**: MAJOR
- **Claim**: "Single-writer" is two distinct claims that must NOT be conflated: (a) at-most-one-writer-thread per process (testable via `threading.Lock` ownership assertion), (b) at-most-one-writer-process per DB file (NOT testable at unit level — SQLite's `BEGIN IMMEDIATE` + `busy_timeout` provides this and the test reduces to "trust SQLite"). For (a), the falsifying-case is: `def test_two_writers_serialize(): q = WriteQueue(evidence_path); results = [None, None]; t1 = Thread(target=lambda: results.__setitem__(0, q.write(...))); t2 = Thread(target=lambda: results.__setitem__(1, q.write(...))); t1.start(); t2.start(); t1.join(); t2.join(); assert both succeeded`. Keep deterministic threading test; Hypothesis stateful is a v0.2 addition.
- **Evidence**: A2 "single-writer queue per DB"; `migrations.py:212` `PRAGMA busy_timeout = 5000`; PLAN §TRACK A invariants do not yet name a concurrency model.
- **Recommendation**: Track A implements `WriteQueue(db_path)` as a thread-local singleton with `threading.Lock`. Test: 2-thread interleave + assertion that lock is held during execute. Document explicitly in module docstring that cross-process serialization is delegated to SQLite (`BEGIN IMMEDIATE` + 5s `busy_timeout`).
- **What-would-change-it**: If Track D's ablation runner spins worker subprocesses, `WriteQueue` must move to a shared FIFO/socket abstraction.
- **Cross-seat**: RELIABILITY owns backpressure. SCHEMA's BEGIN-IMMEDIATE concern (Q2) is the same primitive.

## Q4 — Property-based test design (OWNED)
- **Disposition**: BLOCKER
- **Claim**: This is THE Track A exit-criterion test. Property statement, exact: `∀ table T ∈ EVIDENCE_TABLES, ∀ valid_row r drawn from row_strategy(T), the sequence [INSERT r; UPDATE T SET <any_col>=<any_val> WHERE pk(T)=r.pk] raises sqlite3.IntegrityError matching r'append_only_violation: ' + T, AND [INSERT r; DELETE FROM T WHERE pk(T)=r.pk] raises the same`. Strategy: `@composite def evidence_insert(draw): table = draw(sampled_from(EVIDENCE_TABLES)); parents = draw(_build_fk_closure(table)); return InsertPlan(table, parents, draw(_row_strategy(table)))`. FK closure: recursive — `oracle_verdicts` requires `runs` + `clauses` + `samples_a` + `samples_b` + optionally `judges` + `calibration_events`. Build a topologically-sorted dependency graph FROM SCHEMA INTROSPECTION (`PRAGMA foreign_key_list(<table>)`), not hand-coded. Performance trap: naive @given will rebuild 100 skill rows + 100 clause closures. Use `@settings(max_examples=50, deadline=None, suppress_health_check=[HealthCheck.too_slow])` + session-scoped DB with per-example `BEGIN; ...; ROLLBACK` instead of fresh DB per example. **NOT TESTABLE by this property**: (1) confound detection, (2) calibration drift, (3) cross-DB consistency, (4) the `runs.completed_at` single-shot allowed transition — falsifying case template would FALSELY flag the legitimate NULL→value UPDATE unless the property carves a specific clause.
- **Evidence**: PLAN §TRACK A exit criterion verbatim; `migrations/evidence/0001_initial.sql:183-207` (triggers, plus runs special-case); `migrations/evidence/0002_runs_trigger_split.sql:20-25` (set-once column trigger).
- **Recommendation**: Track A implements `tests/property/test_evidence_append_only.py` with two properties: (P1) for all tables EXCEPT `runs`, `∀ valid r, INSERT then any UPDATE aborts`; (P2) for `runs` specifically, `∀ valid r, INSERT then UPDATE of skill_id|run_kind|config_json|started_at aborts; INSERT then single UPDATE of completed_at succeeds; INSERT then second UPDATE of completed_at aborts`. Schema-introspected FK closure via `PRAGMA foreign_key_list`. `@settings(max_examples=50)`. Session-scoped DB with savepoint-per-example.
- **What-would-change-it**: If a future migration adds a legitimate UPDATE-allowed column to an evidence table (e.g., D5's `runs.terminal_state`), P1 needs the same column-carve treatment P2 has.
- **Cross-seat**: SCHEMA owns the schema-introspection FK closure (their lens). RELIABILITY owns the savepoint-rollback test discipline.

## Q5 — Connection lifecycle
- **Disposition**: MAJOR
- **Claim**: Per-test fresh-DB fixture (current `conftest.py:14-21`) is correct for SMOKE tests but catastrophic for Hypothesis tests at `max_examples=50` × 9 evidence tables × FK closure depth ≈ 4 — 100ms × 1800 = ~3 min if naive. Falsifying-case for lifecycle correctness: `def test_fixture_isolation(evidence_db, request): row_count_before = evidence_db.execute('SELECT COUNT(*) FROM skills').fetchone()[0]; assert row_count_before == 0` — runs across all tests; if any test leaks state, this fails. Hypothesis fixture interaction: `@given` re-invokes the test function body per example, but `@pytest.fixture` instantiates ONCE per test function (not per example). With function-scoped `evidence_db`, all 50 Hypothesis examples share the same DB — which means the property test must use `BEGIN; ...; ROLLBACK` per example or it will accumulate state and the strategy must generate UNIQUE PKs per example or hit PRIMARY KEY violations.
- **Evidence**: `tests/conftest.py:14-21` function-scoped fixture; Hypothesis docs (`@given` reruns the body, NOT the fixture); `migrations.py:208` autocommit mode.
- **Recommendation**: Track A adds a SECOND fixture `evidence_db_savepoint` that wraps each Hypothesis example in `SAVEPOINT hyp_example; ...; ROLLBACK TO hyp_example;`. Document that property tests MUST use this fixture; smoke tests use the existing `evidence_db`. Add `test_hypothesis_savepoint_isolation` that runs 3 examples and asserts row count is 0 between each.
- **What-would-change-it**: If Hypothesis grows a per-example fixture hook in a future release, this gets simpler.
- **Cross-seat**: RELIABILITY owns "what if SAVEPOINT itself fails." SCHEMA owns whether triggers fire correctly inside savepoints.

## Q6 — Admissibility filter on read (CORE)
- **Disposition**: BLOCKER
- **Claim**: This is the canonical PRD §6 falsifiability check and currently has ZERO test coverage. The claim "no admissible evidence ⇒ no claim" (PRD §6, CLAUDE.md "Aggregation rules") demands: (a) the SQL/Python path that feeds aggregation MUST filter by `admissibility_state = 'admissible'` AND join-exclude verdicts whose `clause_id` appears in `confound_events WHERE delta_kind = 'confound_flagged'` for the same run. The schema does NOT have a `confounded` boolean on `oracle_verdicts` — confound state is in a SIDE TABLE indexed by `(run_id, primary_clause_id)`. Falsifying-case: `def test_aggregation_excludes_inadmissible(): insert 10 admissible + 5 inadmissible verdicts; assert aggregator returns N=10 not N=15`. Second: `def test_aggregation_excludes_confounded(): insert 10 admissible verdicts for clause C in run R; insert confound_events row (R, C, delta_kind='confound_flagged'); assert clause C reports UNMEASURED(confounded), not aggregated`. The JOIN is non-trivial: aggregation must LEFT JOIN confound_events ON (run_id, clause_id) WHERE delta_kind = 'confound_flagged' AND assert NULL match.
- **Evidence**: `migrations/evidence/0001_initial.sql:128` admissibility_state CHECK; `0001_initial.sql:142-154` confound_events structure; `0001_initial.sql:215` `idx_verdicts_clause_adm` exists, suggests intent; A11 confound detection.
- **Recommendation**: Track A defines an `aggregation_view` SQL VIEW (read-only, no triggers needed) that pre-joins these filters: `CREATE VIEW admissible_verdicts AS SELECT v.* FROM oracle_verdicts v WHERE v.admissibility_state = 'admissible' AND NOT EXISTS (SELECT 1 FROM confound_events c WHERE c.run_id = v.run_id AND c.primary_clause_id = v.clause_id AND c.delta_kind = 'confound_flagged')`. Track A adds two falsifying-case tests at the view level: inadmissible-excluded and confounded-excluded. The view is the single source of truth — Python aggregation code that bypasses the view fails code review.
- **What-would-change-it**: If A11's confound semantics shift to mark the AFFECTED clause as confounded rather than the PRIMARY, the EXISTS subquery clause changes.
- **Cross-seat**: SCHEMA co-owns the view definition. SECURITY's lens: if attacker can write to runtime.current_calibration, can they retroactively flip admissibility? A3 answers no (write-time snapshot in evidence). Confirm test covers it.

## Q7 — Migration sequencing across worktrees
- **Disposition**: MAJOR
- **Claim**: Current `discover()` at `migrations.py:69-88` glob-sorts by filename. Two worktrees both adding `0003_*.sql` produce a deterministic but WRONG merge: lexicographic sort yields `0003_a.sql` before `0003_b.sql`, both with version=3, both ledger-stamped as `0003_a` and `0003_b` — they COEXIST silently with the same version int. Falsifying-case: `def test_discover_rejects_duplicate_version(tmp_path): write 0003_a.sql + 0003_b.sql; assert discover() raises ValueError('duplicate migration version: 3')`. Currently this test would FAIL (no such guard at `migrations.py:69-88`). The `Migration.version` int collision is invisible because `migration_id` (file stem) is unique. The downstream danger: a developer running `apply_pending` against a DB that has `0003_a` applied but not `0003_b` will silently apply `0003_b` (different `migration_id`, not in ledger) — leading to non-deterministic schema-divergence across machines depending on glob order.
- **Evidence**: `migrations.py:74` `sorted(directory.glob("*.sql"))` — lexicographic; `Migration` dataclass at `migrations.py:53-62` has no uniqueness check on `version`; `applied_records()` keys on `migration_id` not `version`.
- **Recommendation**: Track A adds duplicate-version guard in `discover()`: `seen = {}; for m in out: if m.version in seen: raise ValueError(f'duplicate migration version {m.version}: {seen[m.version]} vs {m.name}'); seen[m.version] = m.name`. Add `tests/test_migration_discover_duplicate_versions`. Add CI/pre-commit check that greps `migrations/{evidence,runtime}/` for duplicate numeric prefixes pre-merge.
- **What-would-change-it**: If migrations move to `importlib.resources` (D8) with a manifest file declaring ordering, the glob-sort vs explicit-order tradeoff flips.
- **Cross-seat**: RELIABILITY owns the merge-conflict prevention angle. SCHEMA owns the "what does duplicate version MEAN semantically" question.
