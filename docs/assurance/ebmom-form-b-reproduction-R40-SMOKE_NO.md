## What the receipt records

It was written at `d39440d` (#441, 2026-09-06) by `scripts/ebmom_form_b_reproduction.py` with
`--column cand_bpB`, `--replicates 40`, root `SMOKE_NOT_CONFIRMATORY`, over the regimes

cell, on the four compared fields (`count`, `of`, `worlds`, `false_worlds`).

`cand_bpB` scores form B on the refused path with **the plug-in on the admitted path**. That is
the part that matters below.

## Why it no longer regenerates

`#442` (`60a6548`) replaced the plug-in on the admitted path with the admission-conditioned
parametric bootstrap. The receipt's own command line, run against production after that,
compares the new admitted path against the old prototype column and reports differing cells
where the committed file records zero.

Nothing under `tests/` named this receipt, so it stayed green while the claim it carries
("production reproduces `cand_bpB`") stopped being true one slice later. That silence is the
defect #450 filed, and it is what the gate below closes.

## The decision: frozen, not regenerated — and why that is the honest option

`#450` permits either. Frozen is correct here for three reasons, each measured on
`agent/issue-360` on 2026-09-08 rather than reasoned from the code.

**1. The receipt's expected input is not in this repository.** The receipt names
`expected_file: "proto-pb-all-R40-SMOKE_NO.json"` and pins it at `expected_sha256:
8192de6d56bfece4d7f2f0e212a7a2f3d66b77629f2de4e301ea424694ec55a0`. That file is not in the
tree — `find . -name "proto-pb-all-R40-SMOKE_NO.json"` returns nothing, and no `proto-pb-*`
artifact is committed anywhere. `--expected` is a required argument, so the documented command
line cannot be run as written without first regenerating that dump.

**2. That input is not byte-reproducible, so the pinned sha256 can never be re-satisfied.**
The dump is produced by the reference directory's `proto_pb.py`, which writes a wall-clock
field per regime (`proto_pb.py:238`, `"seconds": round(time.time() - t0, 1)`). Regenerating it
with `python proto_pb.py all SMOKE_NOT_CONFIRMATORY 40` — possible only after this same ticket
made the reference directory runnable at all — was done twice on 2026-09-08:

| run | sha256 |
|---|---|
| pinned in the receipt (2026-09-06) | `8192de6d56bfece4d7f2f0e212a7a2f3d66b77629f2de4e301ea424694ec55a0` |
| regeneration 1 | `4e85b99d0ba3c095724443f1c2be2c55405a68b00a4410e5a55b2087a6ab7aba` |
| regeneration 2 | `eb67d6bcabbfa3e1d6b0daee61013ce45ce4d361a5553050fc190d148e01731e` |

The two regenerations **are identical once the `seconds` fields are dropped**, and differ only
there (`small_n_bite` 24.9 / 24.6, `tie_heavy_signal` 42.5 / 51.3, and so on). So the dump is
deterministic in every measured quantity and non-reproducible only in wall-clock timing: the
`expected_sha256` pin is unmeetable except by a coincidence of five rounded durations. This is
the same clock-derived-field defect `#452` removed from the reproduction receipt itself; the
prototype dump the receipt compares against still carries it.

**The measured cells, by contrast, reproduce exactly.** Comparing the receipt's own `built`
block — production at `d39440d`, which the receipt records as agreeing with the #441 prototype
— against the `cand_bpB` column of the dump regenerated by the repaired directory: **32 of 32
compared fields equal, 0 differing**, across both regimes, all four cells, and all four
compared fields. The repair therefore reproduces the numbers the reference was frozen to
produce; only the timing field prevents byte identity.

**3. Regenerating would not restore the claim; it would misreport a deliberate change as a
regression.** After `#442` the mechanism on the admitted path is intentionally no longer the
plug-in. Measured on 2026-09-08 by running the receipt's own command line against production
on this branch, with the regenerated dump as `--expected`: exit code 1, `total_differences: 3`,
and every difference in one cell of one regime —

```
[low_heterogeneity] admitted 27/40  3 DIFFER
   DIFF row5c_false_pass_admitted.count:        built=35  expected=39
   DIFF row5c_false_pass_admitted.of:           built=932 expected=1029
   DIFF row5c_false_pass_admitted.false_worlds: built=15  expected=16
[tie_heavy_null]    admitted 0/40  AGREES
```

The differences are confined to `row5c_false_pass_admitted` — the **admitted** path, which is
exactly what `#442` changed; the refused-path cells, which are what form B governs, still agree, and
`tie_heavy_null` — refused in all 40 worlds — agrees entirely. That is the signature of an
intended supersession, not of a regression. A regenerated receipt would record a reproduction
failure against a column production was deliberately moved off, and recording an intended
change as a failed reproduction is less honest than saying plainly that the procedure was
replaced.

Regenerating is affordable — the script is local Monte Carlo with no network or paid call — so
this is not a cost refusal. It is a refusal to restate a superseded measurement as a current
one. `#450`'s other branch, giving the script an explicit mode that scores the plug-in admitted
path, would build new measurement machinery to keep an obsolete claim alive; that is outside
this ticket and is not obviously worth doing.

## What this receipt may and may not be cited for

- **May:** that at `d39440d`, production reproduced the prototype's `cand_bpB` column at R = 40
  on the two named regimes, under the root `SMOKE_NOT_CONFIRMATORY`.
- **May not:** anything about production at or after `60a6548`. It does not claim current
  reproduction and must not be read as claiming it.
- **May not:** anything confirmatory. `is_confirmatory: false`, and the root is a development
  smoke. Nothing here is a result about the estimator.

## The gate

`tests/test_ebmom_form_b_receipt_frozen.py` pins the receipt's bytes to the sha256 above and
requires this twin to keep declaring the freeze. A regenerated or edited receipt turns that
test red, which forces whoever changes it to say here what the new file measures — the
silence #450 filed cannot recur without someone stepping over a failing gate.
